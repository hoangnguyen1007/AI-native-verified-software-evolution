## Executed path and safety conditions

The executable journey is selected directory → bounded filesystem capture → decoding/inventory → build projection or producer-asserted selected source-plan import → permission-checked exact bundle import, optionally with a selected-configuration graph → coordinator ledger → source-set assembly. A valid supplied artifact and consistent graph can produce an exact Java frontend request; a mismatched graph or unavailable artifact leaves structural source rows and typed gaps. The generated-source path creates a new immutable source snapshot with recipe/input/output digests and resolves a real JavaParser consumer. The coordinator records attempts, denied/unavailable outcomes, conflicts, per-gap resolutions and cooperative cancellation at provider boundaries; the journey exposes the same cancellation input without opening an artifact when cancellation precedes the import. Captured acquisition checkpoints replay captured bytes after the live directory changes; partial capture never becomes an exact snapshot.

Exactness relies on an explicitly allowlisted captured producer assertion plus independently checked selected artifact bytes, order, source/build revision and local containment. The allowlist is a trust boundary, not cryptographic producer authentication. The optional resolved graph asserts selected components/variants and must bind every relevant direct declaration and transitive artifact; the importer checks these assertions against classpath names, bytes and context, but does not independently prove how Gradle or Maven made the selection. A dynamic selector can be replayed against a supplied selected version without choosing the newest host cache entry. Captured Spring library resources carry both original archive and selected entry digests; they are not yet converted into semantic registration facts. The importer records release-selected class entry names and digests for a standard multi-release JAR on the classpath, matching the existing frontend's classpath selection rule; this is not JPMS/module-path proof. The default Gradle catalog parser recognizes a bounded literal fragment of `libs.versions.toml`; it does not evaluate Gradle, select variants or turn declarations into resolved artifacts. Range and mutable SNAPSHOT selectors remain unresolved without an imported selection assertion. No target lifecycle was executed.

### V2.1 worker supervision, Slice 1

The `analyzer-filesystem` supervisor executes one fixed, analyzer-owned SHA-256 operation per JVM. The worker receives only captured bytes through bounded IPC; its classpath is assembled from trusted analyzer code locations, its inherited environment is cleared, stderr is discarded, and no target path, build command or script is accepted. The parent bounds input/output bytes, batch size, JVM heap and wall deadline, kills a timed-out or canceled worker, and classifies nonzero exit, malformed response, input mismatch and checkpoint failures without exposing exception text. Each completed unit has an atomic, sealed checkpoint keyed by captured-input and policy identity. A resumed batch reuses validated completed units, reattempts failed units, and preserves the canonical result identity when captured inputs and policy are the same. Failed units expose no successful output and can be projected into `CapabilityGapRecord` with distinct reason and affected obligation. Time, checkpoint location and restored-versus-fresh telemetry are excluded from the result identity.

This is a bounded supervisor/IPC/replay control, **not** a claim that the existing frontend, build adapters, Spring providers or coordinator now execute in worker processes. `-Xmx` limits Java heap, not total process RSS or an OS sandbox; live host failure and wall timeout remain external conditions. Crash/timeout controls establish only the fixed trusted operation's recovery behavior until real provider stages are wired through the protocol. The V2.1 recovery checklist therefore remains partial.

Fresh Slice 1 verification on 2026-09-27: `WorkerProcessSupervisorTest` executed 7 tests with zero failures/errors/skips, covering uninterrupted/restarted identity, process exit, OOM, stack overflow, deadline, active cancellation, malformed IPC, corrupt/stale checkpoint and input mismatch. `.\mvnw.cmd verify -pl analyzer-filesystem -am -q` exited 0; fresh Surefire XML for the participating modules records 457 tests in 58 suites with zero failures/errors/skips. A subsequent authorization-class refinement was verified by rerunning the focused 7-test class; the broader module verification predates that refinement. This is affected-module integration verification, not a new root-reactor gate or a real-repository benchmark.

### V2.1 worker supervision, Slice 2

`AdaptiveRepositoryJourney.resolveSupervised` now runs the captured exact-classpath receipt through the trusted worker before the evidence coordinator may satisfy its requirement or assemble an exact frontend request. The authorization registry requires both `LOCAL_READ` for artifact import and `LOCAL_WRITE` for the worker checkpoint; either missing permission denies the stage before artifact access or worker launch. The supervised attempt has a separately versioned provider and input revision that includes worker policy. Its process failure produces a failed/canceled acquisition attempt and a typed worker capability gap in the same coordinator ledger. Previously observed source structure and the importer's artifact result remain available, but no exact frontend request is emitted. A successful retry after crash/timeout and a later checkpoint replay produce the same canonical journey identity; a policy change invalidates that worker checkpoint. Existing unsupervised `resolve` controls still pass; the implementation retains their prior revision and provider fields.

This stage validates the **receipt bytes** in a worker. Archive expansion and the imported classpath graph are still processed in the parent JVM before this validation; a hung importer is not yet recoverable through this worker boundary. The next stage boundary should isolate that work while preserving bounded artifact provenance and selected-entry evidence.

### V2.1 worker supervision, Slice 3

`resolveSupervised` now captures and rechecks selected archive bytes in the parent, then sends those bytes to a fixed trusted archive worker for bounded ZIP expansion, multi-release class selection and Spring resource capture. The worker receives no target path or command; it uses the authorized checkpoint directory for temporary ZIP inspection. A sealed per-archive checkpoint binds captured digest, target release, selection mode, resource limits and worker policy. Replay excludes checkpoint location from result identity. The importer withholds exact input on worker crash, timeout, cancellation, protocol/checkpoint failure, input/output limit or corrupt archive, while retaining previously observed structure and unaffected artifact receipts. Worker failures have their own typed requirement and `LOCAL_WRITE` authorization; malformed artifact evidence retains artifact acquisition requirements. The existing unsupervised importer retains its prior behavior and identity.

This isolates archive expansion, not artifact file capture/hash, resolved-graph validation, build modeling or frontend/Spring computation. Input is bounded by the configured worker policy (at most 64 MiB) and output by its configured response budget (at most 16 MiB); valid larger archives/resources stay partial with typed limits. `-Xmx` is a JVM heap bound, not an OS RSS or sandbox guarantee. Worker termination cannot guarantee cleanup of its temporary ZIP after a hard kill. No bytecode annotation/default extraction, class-directory import or nested WAR/fat archive semantics follow from selected class digests alone.

They cover selected-entry parity, replay identity, corrupt/stale checkpoint rejection, crash/timeout/retry, archive/path/expansion and input limits, worker start failure and preserved source structure.
