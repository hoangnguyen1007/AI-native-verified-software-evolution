## Durable controller and real recovery revision

**CONFIRMED implementation:** `ExecutionAttempt` and `DurableAttemptStore` record the immutable launch/request and expected task state before reservation, lease or driver calls. `ExecutionController` uses a recoverable multi-record protocol: durable intent → admission reservation → task lease → durable launch intent → returned handle. It never relaunches during recovery. Quiescence is committed before the task termination pointer and reservation release; all revisions and fences are checked. A persistent launch frontier distinguishes never-launched work even after a stop-intent crash. `ControllerTerminationLedger` accepts only its controller-owned registered records, verifies exact launch scope and CAS evidence, and rejects a producer's invented termination digest. This internal authority is not an externally uploadable proof API or a native semantic receipt.

Recovery and cancellation retain capacity when discovery, ownership or termination cannot be verified. Foreign handles are not stopped. Finishing after quarantine records FAILED with termination instead of inventing success. Missing immutable input bytes cannot enter admission/launch. A stale attempt's final close cannot overwrite a newer task fence. Recovery pages preserve a high-water frontier and one outcome per source row, so corrupt evidence retains an explicit failure without blocking independent rows. Task readiness/resource/profile selection still comes from the upstream prevalidated-plan composition; this controller is not a public arbitrary-command API.
